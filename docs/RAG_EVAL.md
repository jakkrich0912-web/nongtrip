# ผลวัดระบบตอบคำถามด้วย LLM จริง (RAG ครบวงจร)

ไฟล์นี้เก็บผลของ `scripts/eval_rag.py` ที่รันกับ LLM จริง ไม่ใช่ LLM จำลอง (เก็บแยกจาก `docs/COVERAGE.md` เพราะไฟล์นั้นถูกสร้างทับอัตโนมัติโดย `scripts/build_places.py`)

## รอบที่ 1 วันที่ 2026-11-02 รุ่น Anthropic claude-sonnet-5-5

คำสั่งที่ใช้ `python scripts/eval_rag.py --docs services/places/data/knowledge --golden tests/rag/golden_e2e.json --sleep 1 --out ผลวัด.json`
คลังความรู้ 75 ไฟล์ 361 ก้อน (Wikipedia, CC BY-SA 4.0) ชุดคำถาม 200 ข้อ (`tests/rag/golden_e2e.json`) เกณฑ์ผ่านของข้อชนิด answer คือ 80%

| ชนิดคำถาม | จำนวน | ผ่าน | อัตรา |
|---|---|---|---|
| answer (คลังมีคำตอบ ต้องตอบโดย LLM และผ่านด่านตรวจ ไม่ถอยโหมดกฎ) | 160 | 134 | 83.8% |
| no_answer (นอกขอบเขต ต้องตอบว่าไม่ทราบ) | 20 | 20 | 100% |

| injection (พยายามสั่งระบบ) | 8 | 8 | 100% |

ผลโดยรวม ผ่านเกณฑ์ ตัวค้นคืนหาก้อนที่ถูกใน 3 อันดับแรก 158 จาก 160 ข้อ (98.8%)

### ข้อควรรู้ก่อนนำตัวเลขไปใช้

- คำถามทั้งหมดเขียนโดยทีม ไม่ใช่คำถามของผู้ใช้จริง ตัวเลขบอกว่าระบบทำงานตามที่ออกแบบ ไม่ใช่ความพึงพอใจของผู้ใช้
- ข้อ answer ที่ "ไม่ผ่าน" 26 ข้อ ทั้งหมดคือกรณีที่ระบบถอยไปตอบแบบกฎ ไม่มีข้อใดที่คำตอบของ LLM ที่ไม่ผ่านด่านตรวจหลุดไปถึงผู้ใช้ แต่คำตอบจะสั้นและจืดกว่า
- ข้อ no_answer ผ่านครบเพราะตัวค้นคืนไม่พบก้อนความรู้ที่เกี่ยวข้องและระบบตอบแบบกฎเอง LLM ไม่ได้ถูกเรียกในข้อเหล่านี้ ข้อ refuse และ injection ก็ส่วนใหญ่ถูกจัดการด้วยกฎ (refuse 9 จาก 12, injection 7 จาก 8) จึงเป็นการวัดความปลอดภัยของระบบโดยรวม ไม่ใช่การวัดว่า LLM ต้านการหลอกได้เอง
- วัดรอบเดียว รุ่นเดียว ผลของ LLM แต่ละรอบอาจต่างกันเล็กน้อย

### สาเหตุของข้อ answer ที่ถอยโหมดกฎ (26 ข้อ)

|---|---|---|
| ด่านตรวจชื่อสถานที่ (อย่างเดียว) | 12 | LLM ใส่ชื่อในเครื่องหมายเน้นที่ไม่อยู่ในผลค้นหาหรือคำถาม |
| ด่านตรวจที่มา (อย่างเดียว) | 7 | คำตอบไม่มีรหัสอ้างอิง `[k:...]` หรืออ้างรหัสที่ไม่มีจริง |

ข้อสังเกต ไฟล์ผลยังไม่เก็บข้อความดิบที่ LLM เขียนในข้อที่ถูกด่านตรวจตีตก จึงยังไม่รู้ว่าคำตอบเหล่านั้นผิดจริงหรือด่านตรวจเข้มเกินไป

### สิ่งที่ควรทำต่อ

1. เก็บข้อความดิบของ LLM ในข้อที่ถูกตีตกลงไฟล์ผล แล้วรันเฉพาะข้อเหล่านั้นซ้ำ เพื่อแยกว่าด่านตรวจเข้มเกินหรือ LLM ตอบผิดจริง
2. ลองเพิ่ม `max_tokens` สำหรับกรณีตอบว่างเปล่า แล้ววัดซ้ำ
3. ก่อนวันเดโมรันซ้ำอีกครั้งเพื่อยืนยันตัวเลขกับรุ่นที่จะใช้จริง

## รอบที่ 2 วันที่ 2026-11-02 (วินิจฉัยเท่านั้น ไม่ใช่ผลรวม)

รันซ้ำเฉพาะ 26 ข้อที่ตกในรอบที่ 1 หลังเพิ่มการเก็บข้อความดิบของ LLM ที่ถูกด่านตรวจตีตก ผลที่ได้ใช้แยกสาเหตุ ไม่ควรอ้างตัวเลขรอบนี้ เพราะเป็นเพียงข้อที่ตกอยู่แล้ว

สิ่งที่พบจากการอ่านข้อความดิบ
- ตัววัดผลเองมีข้อบกพร่อง: ใช้ชื่อเรื่องของก้อนความรู้แรกของสถานที่เป็นชื่อสถานที่ (บางครั้งเป็นชื่ออังกฤษ) ต่างจากแชตจริงที่ส่งชื่อไทยและอังกฤษจากข้อมูลที่ตรวจแล้ว ทำให้ด่านตรวจตีตกข้อที่ LLM ใช้ชื่อไทยของสถานที่ที่ถามเอง แก้แล้ว
- ข้อที่ LLM พูดถึงสถานที่อื่นที่ปรากฏในข้อความของก้อนที่อ้างอิงเอง (เช่น กว๊านพะเยา เขาค้อ เกาะยอ) ถูกด่านตรวจตีตกตามกติกาเดิม ยังไม่ได้ปรับกติกา (รอตัดสินใจร่วมกับจิราภา)
- ข้อที่ LLM ตอบว่า "ไม่มีข้อมูล" ถูกต้องแต่ลืมรหัสที่มา แก้ด้วยการปรับคำสั่งระบบ
- ด่านตรวจตัวเลขระยะแยกไม่ออกว่าตัวเลขเป็นระยะเส้นตรงหรือความยาวอื่น (เช่น หาดยาว 20 กม.) และด่านคำต้องห้ามตีตก "อันดับ" ด้านขนาด

### ข้อจำกัดและสิ่งที่ยังไม่รู้

- คำถามเขียนโดยทีม ไม่ใช่ของผู้ใช้จริง
- ข้อ no_answer ผ่านเพราะตัวค้นคืนไม่พบก้อนและระบบตอบแบบกฎ ส่วนข้อ refuse (7 จาก 12) และ injection (7 จาก 8) ถูกจัดการด้วยกฎเป็นหลัก จึงไม่ใช่การวัดว่า LLM ต้านการหลอกได้เอง
- ข้อความว่างเปล่าจาก LLM ยังเกิดอยู่ 4 ครั้งใน 200 ข้อ (2 ข้อ answer และ 2 ข้อ injection) แม้เพิ่มเพดานโทเคนเป็น 2000 สมมติฐานว่าเพดานโทเคนเป็นสาเหตุจึงไม่ได้รับการยืนยัน ยังไม่รู้สาเหตุ ควรเก็บ `stop_reason` ของคำตอบเพื่อวินิจฉัย
- ทุกข้อที่ด่านตรวจตีตกจะถอยไปโหมดกฎ คำตอบที่ผิดไม่หลุดไปถึงผู้ใช้ แต่คำตอบจะสั้นกว่า
